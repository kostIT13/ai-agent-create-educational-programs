# План работ: вертикальный срез → полный пайплайн

> Статус: актуальный рабочий план (обновляется по мере выполнения).
> Стратегия: **вертикальный срез вместо ширины** — сначала «бриф → структура курса» насквозь,
> затем наращиваем агентов, RAG, экспорт и фронт.
>
> **Контекст хакатона (обновлено):** заказчик — **АЦР** (Магас), кейсодатель — **GigaCowork** (Сбер).
> **Инфраструктура и модели Cloud.ru — цель по ТЗ, доступы пока не выданы** → LLM-слой оставляем
> на текущем OpenAI-совместимом клиенте (переключение на Cloud.ru EFM: GigaChat/Qwen/DeepSeek —
> смена `BASE_URL`/моделей в `.env` перед защитой).
> Два шаблона программ АЦР: №1 ДПП ПК/стажировка (273-ФЗ + приказ Минобрнауки № 499, профстандарты,
> виды часов ЛК/ПР/ЛБ/СРС/ИА) и №2 общеразвивающая (приказ Минпросвещения № 629, ЗУН,
> лекции/практика/СР/ИА). Примеры — в [`dataset/`](../dataset/main_task.txt:1).
> Полный контекст — §0 [`plan.md`](plan.md:38).
> **Метрики ТЗ:** каркас любой программы ≤ 3 мин; полный комплект 72 ч ≤ 20 мин; объёмы 16–500 ч.
>
> **Принцип архитектуры:** вся бизнес-логика живёт в сервисных функциях без привязки к FastAPI
> (`create_course(brief) → job_id`, `get_course(id)`, `edit_competencies(...)`, ...). REST, SSE
> и MCP — три тонких «входа» в одно ядро; если в адаптере появляется логика — её место в сервисном слое.

## Этап 9. MCP-интеграция (после стабилизации сервисного слоя)

**Суть:** MCP — тонкий слой-адаптер, НЕ замена ядра. Качество курса определяют схемы, промпты,
RAG, валидаторы и Critic; MCP лишь открывает доступ к системе извне.

### A. Наша система как MCP-сервер (FastMCP) — приоритет

Отдельный модуль `mcp_server/`, который **импортирует те же сервисные функции**, что и FastAPI
(никакой бизнес-логики внутри). Паттерн «запустил → опрашивай»: генерация 5–20 мин, а MCP-вызов
короткий, поэтому `create_course` сразу возвращает `job_id`, дальше клиент опрашивает статус.

| Тул | Что делает |
|---|---|
| `create_course(brief)` | создаёт курс + джобу, возвращает `job_id` |
| `get_job_status(job_id)` | прогресс и текущий навык |
| `get_course(id)` | граф курса или его часть (шаблон, компетенции, модуль) — **гранулярно** |
| `edit_competencies(id, patch)` | правка на чекпоинте |
| `regenerate_module(id, module_id, comment)` | точечная перегенерация |
| `export_course(id, fmt)` | ссылка на DOCX / PPTX / ZIP / LMS |

Требования: гранулярные ответы; авторизация (для stdio — токен, для streamable HTTP — полноценная);
если в `mcp_server/` появляется логика — вернуть её в сервисный слой.

Польза: методист работает из удобного клиента («создай ПК на 72 часа по данным на Python, покажи
компетенции, сократи модуль 3») без нашего фронтенда; плюс философия GigaCowork (навыки) получает
вторую точку входа.

### B. Наши агенты как MCP-клиенты (langchain-mcp-adapters) — опционально

Только если понадобится внешний поиск актуальных стандартов и инструментов (направление «сверх
плана» — актуализация программ). Референсы веб-тулов — недоверенные: оборачивать в `<source>`,
мокать/кэшировать в evals, деградировать без внешних серверов.

### Когда делаем

- **Сейчас MCP не трогаем.** Приоритеты: RAG/нормативная база (Этап 4) и Critic (Этап 5).

## Этап 10. Observability: MLflow (единый слой вместо Langfuse + RAGAS)

**Решение:** MLflow закрывает трейсинг, стоимость и evals — на одну систему меньше, чем в plan.md.

- [ ] Сервис `mlflow` в docker-compose: backend store — отдельная БД того же Postgres,
      артефакты — в volume. НЕ дефолтный SQLite.
- [ ] `mlflow.langchain.autolog()` — трейсы LangGraph: каждый invoke() графа = дерево спанов
      по навыкам и LLM-вызовам.
- [ ] Токены и стоимость — автоматически; проверить расчёт для моделей текущего провайдера
      (при переключении на Cloud.ru EFM — проверить цены/имена моделей по выданным доступам);
      при отсутствии цен — добавить вручную/из `usage_log`.
- [ ] Async: при необходимости `run_tracer_inline=True` для корректной вложенности спанов.
- [ ] Прямые вызовы мимо LangChain (LLMClient/fallback) — autolog на реальном клиенте, иначе дыры.
- [ ] Два эксперимента: `course-runtime` и `course-evals`.
- [ ] Связка с БД: `mlflow trace_id` в таблицу `events` + теги `course_id`, `job_id`, `node`,
      `prompt_version` → из фронта по клику на узел открывается трейс.
- [ ] Prompt Registry: версионирование и продвижение промптов из `agent/prompts/`.
- [ ] Безопасность данных: закрыть доступ к UI, редакция PII.

## Этап 11. Prod-практики и безопасность

1. **Бюджет и лимиты на джобу**: максимум токенов/стоимости на курс (Cloud.ru), остановка при
   превышении, семафор на параллельные вызовы (Send) — защита от зациклившегося Critic'а.
2. **Версионирование схемы CourseGraph**: `schema_version` в `course_versions` + функции миграции.
3. **Безопасность**:
   - референсы и результаты внешних инструментов — недоверенные: обёртка `<source>` (уже в RAG);
   - проверка вывода: утечка системных промптов, ссылки на несуществующие источники;
   - лимиты размера и типов загружаемых файлов (.docx/.pdf/.txt).
4. **Операционная наблюдаемость без LLM**: структурные логи с `job_id`/`course_id`, метрики API,
   Sentry для исключений.
5. **LLM-шлюз**: сейчас свой `LLMClient` (retry + fallback между моделями провайдера + учёт токенов);
   при росте функциональности — переход на LiteLLM; на Cloud.ru (после выдачи доступов) — сам
   `LLMClient` достаточно гибок: меняются `BASE_URL`/модели, логика не трогается.
6. **Фичи для пользователя**: diff между версиями, gap-анализ загруженной программы
   (сверка часов — как в §0.4 plan.md), heatmap «компетенция × модуль» с трассировкой до источника.
